Bug Reports

Real bugs found while testing CoCreationMap. Click a card to expand the details.

Critical

Weak Passwords Accepted on Sign-Up

Module: Registration · Type: Security

click for details ↻

Steps to Reproduce

1. Fill in all required registration fields.
2. Enter a password missing an uppercase letter and a special character.
3. Accept the Terms of Use.
4. Click "Create Account".

Expected

Account creation should be blocked until the password meets all policy rules (8+ chars, upper & lowercase, number, special character).

Actual

The account is created successfully even though the password fails every policy rule.

Why Critical

A security control is fully bypassed, exposing every new account to weak-credential risk. Raised from the original "High" rating.

High

Connection Roles Reversed (Sender ↔ Recipient)

Module: Connections · Type: Functional

click for details ↻

Steps to Reproduce

1. Company B sends a connection request to Company C.
2. Refresh the page.
3. Check the "Sent"/"Received" tabs and button states for both companies.

Expected

The sender sees the request under "Sent" with a "Remove request" option; the recipient sees it under "Received" with Accept/Decline options.

Actual

After refreshing, the roles swap: the sender sees it as "Received" and the recipient sees "Sent" with "Remove request", flipping every available action. Only "Accept" still works.

Medium

Missing "Confirm Password" Field on Registration

Module: Registration · Type: Functional (Missing per Acceptance Criteria)

click for details ↻

Steps to Reproduce

1. Open the registration form.
2. Look for a "Confirm Password" field next to "Password".

Expected

A required, hidden-by-default "Confirm Password" field with a show/hide icon, validated against the password field.

Actual

The field doesn't exist, so matching validation and the "Passwords must match" message can't be tested because it was never implemented.

Priority Note

Downgraded from "High". It doesn't block registration or expose a security flaw, but leaves a spec'd safeguard unimplemented.

Low

Required "Location" Field Missing Asterisk

Module: Registration · Type: UI

click for details ↻

Steps to Reproduce

1. Open the registration form.
2. Check the "Location" field.

Expected

The Location field should display the (*) required-field indicator, like every other mandatory field, per the User Story.

Actual

Location is required to complete registration but shows no (*) indicator, inconsistent with the rest of the form.

Priority Note

Downgraded from "Medium". Purely a cosmetic inconsistency with no functional or blocking impact.

Cypress Login Automation

Stack: Cypress + JavaScript + Page Object Model

A small automation suite testing a login flow, structured with the Page Object Model: a LoginPage class encapsulates selectors and actions, keeping test specs clean and reusable.

// loginPage.js
class LoginPage {
  selectorsList() {
    return {
      usernameField: '[name="username"]',
      passwordField: '[name="password"]',
      loginButton: '.oxd-button',
    };
  }

  accessLoginPage() {
    cy.visit('/auth/login');
  }

  loginWithUser(username, password) {
    cy.get(this.selectorsList().usernameField).type(username);
    cy.get(this.selectorsList().passwordField).type(password);
    cy.get(this.selectorsList().loginButton).click();
  }
}
export default LoginPage;
// user.spec.cy.js
it('logs in successfully', () => {
  loginPage.accessLoginPage();
  loginPage.loginWithUser(userData.userSuccess.username, userData.userSuccess.password);
  cy.location('pathname').should('equal', '/web/index.php/dashboard/index');
});
